# Advanced Search Agent ("Search Agent") — recherches complexes, plusieurs AI Tools

Ce document décrit le 15e Agent du Copilot : un moteur de recherche qui comprend des critères complexes (période, seuil de montant, absence de correspondance) exprimés en langage naturel, et les vérifie en combinant **plusieurs AI Tools** de modules différents. Point d'entrée : `agents/advancedSearchAgent.js`, interprétation des critères : `reasoning/searchQueryParser.js`, mise en mots : `reasoning/searchAnswerBuilder.js`.

## Pourquoi un NOUVEAU fichier, pas une réactivation de `searchAgent.js`

`agents/searchAgent.js` existe déjà, porte le nom `search_agent`, mais gère l'intention `documentation_question` en RAG pur (aucun Tool) — un concierge documentaire générique, remplacé par `CrmAssistantAgent` et volontairement **laissé non câblé** (`agents/manifest.js`, code conservé). Ce fichier est une chose complètement différente de ce qui est demandé ici (comprendre des recherches sur les DONNÉES du CRM, pas répondre à des questions sur l'usage du CRM). Repurposer ce fichier aurait fait mentir sa propre documentation (`CRM_ASSISTANT.md`, `README.md`) sans raison — ce nouvel Agent (`advanced_search_agent`, intention `advanced_search`) est un fichier et un nom distincts, `searchAgent.js` reste inchangé.

## Les 4 exemples demandés → ce qui est réellement possible, honnêtement

| Exemple demandé | Support | Pourquoi |
|---|---|---|
| "Montre les projets créés en juin." | ✅ Pleinement supporté | `list_projects` accepte `dateFrom`/`dateTo` (des clés non déclarées dans son schéma Joi mais réellement lues par `project.service.js` puis transformées en `WHERE "createdAt" BETWEEN ...` par `project.repository.js::buildBaseWhere`) — un filtre RÉEL, pas un post-traitement. |
| "Quels devis dépassent 50 000 € ?" | ❌ Non supporté LITTÉRALEMENT, alternative proposée | Aucune donnée de montant n'existe pour un devis dans ce CRM : `ProjectDevis` (le modèle du document devis) ne contient QUE `nomDevis`/`fileUrl`/`mimeType` — pas un manque de Tool, un manque de DONNÉE. L'Agent le dit explicitement, puis propose — clairement étiquetée comme une donnée DIFFÉRENTE — la même recherche sur `Project.montantMarche` (le montant du marché, contractuel), la seule métrique monétaire de projet réellement filtrable. |
| "Quels clients n'ont jamais acheté ?" | ❌ Non supporté, aucune alternative honnête possible | Aucun Tool ne liste les `CommercialContact` individuellement (seulement des KPI agrégés) et aucun champ ne trace un achat — le proxy le plus proche (`pipelineStage: "Gagné"`) n'est agrégé par aucun Tool existant. L'Agent le dit explicitement plutôt que d'inventer une liste. |
| "Quels commerciaux n'ont aucune activité cette semaine ?" | ⚠️ Supporté par un PROXY documenté, admin-tier uniquement | `get_commercial_contact_kpi` (vue globale, réservée admin-tier) expose `usersPerformance[].lastActivity` (= `MAX(commercial_contacts.updatedAt)` par commercial) — l'Agent compare cette date au lundi 00:00 de la semaine en cours. C'est une mesure de "dernière mise à jour d'une fiche contact", pas de "toute activité" au sens large (appels non journalisés, actions hors fiche...) — étiqueté "proxy" explicitement dans chaque réponse. Un appelant non admin-tier reçoit une vue personnelle sans `usersPerformance` : la recherche répond alors qu'elle nécessite un accès de type direction, plutôt que de deviner. |

## Comment un critère est reconnu — `reasoning/searchQueryParser.js`

- **Période** : `parseMonthDateRange(message)` cherche un nom de mois français (`janvier`..`décembre`, accentué ou non) parmi les tokens du message (`utils/tokenize.js` — pas de désaccentuation, donc les deux formes sont dans la table `MONTHS_FR`), plus une année à 4 chiffres optionnelle (sinon l'année en cours). Sans mois reconnu : `supported: false`, jamais une plage fabriquée.
- **Seuil de montant** : `parseAmountThreshold(message)` cherche un motif `<chiffres avec espaces>€|euros` par expression régulière sur le texte BRUT (pas le tokenizer, qui aurait coupé "50 000" en deux tokens) ; un mot d'infériorité (`inférieur`, `dessous`, `moins`) bascule l'opérateur sur `lt`, sinon `gt` par défaut (le cas demandé, "dépassent"). Le filtrage réel (`filterByThreshold`) s'applique ensuite sur les données DÉJÀ renvoyées par `list_projects` — `list_projects` n'a AUCUN filtre serveur sur `montantMarche` (vérifié : ni dans son schéma Joi, ni dans `project.service.js::listProjects`, ni dans `buildBaseWhere`) — c'est un post-traitement de données réelles (jamais un chiffre inventé), au prix de récupérer jusqu'à 200 projets triés par `montantMarche DESC` pour les filtrer côté Agent.
- **"Cette semaine"** : `computeStartOfWeek(now)` — lundi 00:00 de la semaine de `now` (convention française) — puis `usersWithNoActivitySince(usersPerformance, startOfWeek)`.

## Comment un type de recherche est déclenché dans l'Agent

`QUERY_DEFINITIONS` (`agents/advancedSearchAgent.js`) — même mécanisme que `DOMAIN_DEFINITIONS` de `BusinessAnalystAgent` : un marqueur lexical LOCAL à cet Agent (jamais un mot-clé du catalogue d'intentions global) déclenche chaque type de recherche ; **plusieurs peuvent se combiner dans une même question** ("projets créés en juin ET montant > 50 000 €" déclenche les deux, `list_projects` appelé une fois par critère distinct — pas de fusion inventée entre deux filtres différents). Aucun marqueur reconnu → un menu honnête de ce qui EST cherchable aujourd'hui (`searchAnswerBuilder.js::CAPABILITIES_MENU`), jamais une tentative de deviner l'intention de l'utilisateur.

## L'intention `advanced_search` — pourquoi les 4 exemples originaux ne suffisent pas à router

Le routeur d'intentions est purement lexical, sans stemming (voir tout le reste de ce Copilot) : les 4 exemples fournis ("Montre...", "Quels clients...", "Quels devis...", "Quels commerciaux...") ne contiennent AUCUN des mots-clés retenus pour cette intention (`recherche(s)`, `rechercher`, `trouve(r)`, `cherche(r)`, `filtrer`, `filtre`) — vérifié : avant cet ajout, ces 4 messages ne matchaient AUCUNE intention du catalogue et retombaient sur `general_chat`. Une formulation réaliste avec un verbe de recherche explicite ("Recherche...", "Trouve...", "Cherche...") est donc nécessaire pour atteindre cet Agent — documenté ici plutôt que découvert silencieusement en production. Les scénarios de corpus (`search-01`..`search-09`) utilisent volontairement "chantiers" plutôt que "projets" dans les critères de période/montant : le mot "projets" appartient déjà à l'intention `projects` (enregistrée bien plus tôt dans le catalogue) et gagnerait toute égalité de score contre le seul mot-clé de recherche présent.

## Ce qui n'a pas été fait (délibérément)

- **"Clients n'ayant jamais acheté"** — aucune alternative honnête n'existe (voir tableau ci-dessus) ; contrairement au cas "devis", il n'y a même pas de proxy à proposer.
- **Un vrai Tool de filtrage serveur sur `montantMarche`** — non ajouté ; le post-traitement sur 200 projets triés est suffisant pour l'usage attendu (un Copilot conversationnel, pas un export de masse) sans modifier `project.repository.js`.
- **Une compréhension de dates arbitraires** ("entre le 3 et le 17 juillet", "le trimestre dernier") — seuls un nom de mois + année optionnelle sont reconnus ; toute autre formulation de période retombe honnêtement sur "Aucun mois reconnu dans la demande", jamais une plage devinée.
- **"Activité" au sens large pour les commerciaux** (appels, relances, tout type d'action) — seule la dernière mise à jour d'une fiche contact commercial (`lastActivity`) est disponible et agrégée par Tool ; un `CommercialContactAction` avec `dateAction` existe bien en base mais n'est exposé par AUCUN Tool MCP — non ajouté dans cette passe (aurait nécessité un nouveau Tool, hors périmètre "utiliser les AI Tools existants").
